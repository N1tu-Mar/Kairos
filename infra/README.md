# Kairos on AWS

Terraform for the backend. The frontend stays on Vercel — it is a Next.js
app and that is what Vercel is for; only `KAIROS_API_URL` and
`KAIROS_API_TOKEN` connect the two, both set server-side in the Vercel
dashboard, never `NEXT_PUBLIC_*`.

```
EventBridge Scheduler ──▶ ALB ──▶ ECS Fargate (1 task: FastAPI + pipeline) ──▶ Bedrock
        (daily, Bearer)             │                    │
Vercel (Next.js) ───────────▶ ──────┘                   EFS (/data: SQLite + spend ledger)
```

## What this answers from `../incomplete.md`

The *Scheduled pipeline invocation* section listed the open questions. The
positions taken here:

- **Where does the pipeline deploy?** With the API, in one Fargate task.
  A run is CPU-idle waiting on Bedrock and Grants.gov; it does not deserve
  its own compute tier yet.
- **How does the trigger invoke it?** EventBridge Scheduler calls the
  existing `POST /founders/{id}/runs` through an API destination. One code
  path into a run whether a person or the schedule asks — exactly what the
  endpoint's docstring promised.
- **How does it authenticate?** The same `KAIROS_API_TOKEN` bearer token the
  dashboard's proxy sends. The token is generated by Terraform, stored in
  Secrets Manager, injected into the task, and embedded in the EventBridge
  connection. No second credential system.
- **Overlapping runs?** The schedule fires daily and a run finishes in
  minutes, so overlap is a retry-storm scenario, not a steady-state one:
  retries are capped at 1. A real lock (a `runs` row with a lease) is the
  next step if the cadence ever tightens.
- **Retry and failure reporting?** One retry within the hour, then the
  structured run logs in CloudWatch are the record. An alarm on
  `sources_failed` is deliberately not built yet.
- **Database when API and worker separate?** They don't separate. SQLite on
  EFS is single-writer in practice, so `desired_count = 1` and deploys stop
  the old task before starting the new one. The day two writers are needed,
  the answer is RDS Postgres, not a second SQLite reader.

The browser owns none of this, as `incomplete.md` requires: Kairos keeps
searching with no founder's laptop open.

## Deploy

```bash
cd infra
terraform init

# Model IDs are discovered, never guessed (agent/config.py):
aws bedrock list-foundation-models --region us-east-1 \
  --query 'modelSummaries[?contains(modelId, `anthropic`)].modelId'

terraform apply \
  -var bedrock_model_reasoning=... \
  -var bedrock_model_classify=...

# Build and push the image the service will pull:
aws ecr get-login-password | docker login --username AWS \
  --password-stdin "$(terraform output -raw ecr_repository_url | cut -d/ -f1)"
docker build -t "$(terraform output -raw ecr_repository_url):latest" ..
docker push "$(terraform output -raw ecr_repository_url):latest"
aws ecs update-service --cluster kairos --service kairos-backend --force-new-deployment
```

Then point the frontend at it (Vercel → Settings → Environment Variables):

```
KAIROS_API_URL   = <terraform output backend_url>
KAIROS_API_TOKEN = <aws secretsmanager get-secret-value --secret-id kairos/api-token --query SecretString --output text>
```

## Deliberate shortcuts, written down

- **Default VPC, public subnets, public task IP.** Wrong for anything with
  real users; fine for a single-founder demo, and the task's security group
  only admits the ALB anyway.
- **HTTP unless `certificate_arn` is set.** The bearer token crosses the
  wire, so plain HTTP is demo-grade only. Provide an ACM certificate and
  port 80 becomes a redirect.
- **Bedrock `Resource = "*"`.** Scoping to model ARNs requires region-exact
  IDs; tighten once the two model variables stop changing.
- **No CI.** `docker build` + `terraform apply` from a laptop is the
  pipeline. Out of scope by the project's own rules.
- **CORS is code, not config.** The Vercel origin list lives in
  `api/main.py::ALLOWED_ORIGINS`; a new production domain means a code
  change there, on purpose — an env-driven origin list is how a wildcard
  sneaks in.
